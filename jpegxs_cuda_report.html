SVT-JPEG-XS エンコーダ CUDA移植

01 / 08

要旨

SVT-JPEG-XS(Intel OpenVisualCloudが公開するISO/IEC 21122実装)のエンコーダを、4K・10bit静止画1枚を16ms以内(60fps相当の理想目標)、遅くとも33ms以内(30fps相当の現実目標)で処理することを目指してCUDAへ移植した。単なる逐次Cコードの機械的な並列化ではなく、規格自体が持つバイトアライメント境界やprecinct間の独立性を利用し、ステージごとに異なる並列アルゴリズムを設計している。

正しさの検証は二段構えで行った。CPU参照実装とのビット完全一致(bit-exact)を全工程・全回帰テスト(12000件超)で維持したうえで、それとは独立に ISO/IEC 21122-5 公式リファレンスソフトウェア(通称 XSM)による復号可能性も確認した。後者の検証過程でCUDA移植そのものとは無関係な、ベースのC実装側の規格適合バグ2件も発見・修正している(7章)。

02 / 08

背景: SVT-JPEG-XSというソフトウェアと、そのC実装の設計

SVT(Scalable Video Technology)は Intel が公開するオープンソースのメディア/コーデック実装群の総称で、SVT-AV1・SVT-HEVC・SVT-VP9 などの兄弟プロジェクトを持つ。SVT-JPEG-XS はその ISO/IEC 21122(JPEG XS)実装にあたり、公開元は Intel の OpenVisualCloud organization、ライセンスは BSD-2-Clause-Patent である。本プロジェクトへは git submodule ではなく、ある時点のソースツリー一式をスナップショットとして取り込み、その上に Source/Lib/Encoder/CUDA/ 以下としてCUDA実装を積み上げている。

移植の出発点を正しく理解するうえで重要なのは、SVTのC実装が ISO 公式リファレンスソフトウェア(XSM, intoPIX SA / Fraunhofer IIS / Canon Inc著作)そのままの素朴な実装ではなく、教科書的な高速化を一通り実装済みの状態だったという点である。両者をソースコードレベルで比較すると、次の4点で設計思想が異なる。

SVT C実装 と ISO参照ソフト(XSM)の設計上の違い(いずれもビットストリーム自体は変えない、計算戦略の差)
観点SVT (このプロジェクトの移植元)ISO参照ソフト (XSM)
GTLI/truncation決定BinarySearch.c による汎用二分探索規格書の記述どおり逐次評価する線形探索
ビットコスト計算significance/gcliヒストグラムを事前集計したLUTの引き当て都度計算(正確性重視、キャッシュ構造なし)
SIMD最適化SSE2/SSE4.1/AVX2/AVX512、RTCD経由で実行時ディスパッチ(76関数)ポータブルなスカラC実装
並列化アーキテクチャステージ分割パイプライン + precinct単位マルチスレッドシングルスレッド逐次処理

したがってCUDA移植は、「素朴な参照実装を並列化する」のではなく、既に二分探索・LUTキャッシュ・SIMD・マルチスレッドパイプラインで最適化されたC実装を上回ることを求められる移植だった。この前提は6章のCPUマルチスレッド版との速度比較にも直結する。

03 / 08

並列化を可能にした規格特性

SVTのエンコーダは実際には Init(1スレッド)→ Dwt(componentごとの別スレッドプール)→ Pack(DWT・GC・レート制御・量子化・ビットストリームパックが1関数チェーンに密結合)→ Final という3〜4段構成になっている。この構造をコード上で精査した結果、GPU並列化の設計を成立させる3つの事実が確認できた。

(a)

gc_precinct_stage_scalar_loop_c が行う significance / gcli 算出は、4係数グループ単位の OR演算 + log2 のみで構成され、精度内・精度間を問わず完全に独立している。

(b)

rate_control_precinct() は precinct 単位で完結する二分探索であり、4K画像で数千個におよぶ precinct 同士に依存関係がない(垂直予測 VPRED を無効化したデフォルト構成を前提とする)。

(c)

align_bitstream_writer_to_next_byte() が precinct・line単位で頻繁に呼ばれ、ビットストリームは規格上バイト境界でアライメントされる。JPEG XS が低遅延・並列実装を明示的に意図した規格である証拠であり、JPEG2000の算術符号化のような全体逐次依存は存在しない。

重要な限定条件: MOVE_PADDINGモードは対象外

事実(b)の「precinct間に依存関係がない」は、VPRED無効に加えてもう一つ前提を置いている。SVTのレート制御には RC_CBR_PER_PRECINCT(均等配分、precinct間独立)と RC_CBR_PER_PRECINCT_MOVE_PADDING(ライブラリのデフォルト。各precinctの使い残しバイトを次のprecinctへ繰り越す、平均で面積の約3%相当)の2モードがあり、後者は繰り越しによってprecinct間に真の逐次依存を生む。この依存は、事前計算した予算配列をホスト側で用意してGPUへ渡す本移植のバッチ設計とは両立しないため、CUDA移植は繰り越しのないRC_CBR_PER_PRECINCTのみをスコープとし、デフォルトであるMOVE_PADDINGモードは対象外とした。呼び出し側はCUDA経路を使う場合、このモード選択を明示する必要がある。

この3点により、DWT・量子化・GCだけでなく、レート制御とビットストリームパッキングまで含めてGPU並列化の設計が成立する見込みが立った。裏を返せば、規格がバイト境界での分断を許していなければ、パッキング段は原理的にGPU向きではなかった。

05 / 08

Cと異なるアルゴリズム・並列化の核心

ここが本移植の本題である。各ステージについて、Cの逐次/スレッド単位の実装をどのような並列アルゴリズムへ置き換えたかを示す。

5.1 DWT — shared memoryタイル化

フレーム全体 18.4ms → 約7ms(タイル化直後)

5/3可逆リフティングは、高域係数 hf が入力のみに依存して完全並列に計算でき、低域係数 lf は確定済みの hf のみに依存して並列計算できるという性質を持つ。この性質を使い、水平方向のリフトカーネルを「1スレッド=1行の逐次処理」から「1行=1 CUDA block によるshared memory協調タイル処理」へ書き換えた。数式・境界処理自体は変更せず、メモリアクセスパターンとスレッド割当のみを再設計している。

C / 移植前
1スレッドが1行(または1列)を先頭から末尾まで逐次リフト
CUDA
1ブロックが1行を担当し、halo込みタイルをshared memoryへロードして協調計算

実機ではDWTがメモリ帯域律速(演算強度 約0.44 ops/byte)であることが判明しており、現状は理論ピーク帯域の約29%しか使えていない。graph1全体(NLT+DWT+GC+RC-LUT)の8〜9割をDWTが占め、現時点で最大の残存ボトルネックである(6章、8章)。

5.2 GC (gcli / significance) — 完全並列カーネル

依存ゼロ、単純elementwise化

4係数グループ単位の OR演算 + log2 のみで構成されるため、C側の逐次ループをそのまま「1スレッド=1グループ」の完全並列カーネルへ置き換えるだけで済む。精度内・精度間の依存が存在しないことが3章の事実(a)で確認済みだったため、設計上の工夫を要さなかった数少ないステージ。

5.3 レート制御 — ブロック内完結の二分探索

追加カーネル起動なし

探索アルゴリズム自体はC版の二分探索を踏襲しつつ、precinct を1つの CUDA block に割り当て、コスト計算をブロック内リダクションで行うことで、探索ループ全体をブロック内で完結させた。これにより複数回のグローバル同期を伴うカーネル再起動を避けている。

5.4 量子化 — 1次元逐次ループから2次元gridへ

単体 11.5ms → 0.78ms(約14.7倍)

量子化は係数ごとに完全独立で、DWTのような隣接依存を持たない。にもかかわらず初期実装は「1スレッド=1行、幅方向はforループで逐次処理」というCの構造をそのまま引き継いだ素朴な移植になっていた。この点は長らく見過ごされ、Pack段の最適化(5.5節)に注力していた時期には「量子化+パック」を1つの区間として計測していたため、量子化側の非効率が表面化していなかった。

移植当初
1スレッド=1行、幅方向は逐次forループ(Cの行単位ループを1:1移植)
修正後
2次元grid(dim3 block2d(32,8))、1スレッド=1係数。数式・分岐は無変更、インデックス計算のみ書き換え

内訳を分離計測して初めて「Packではなく量子化こそが真のボトルネック」と判明し、この1点の修正でフレーム全体のwarm時間が約20〜21msから約9〜10msへ、約2.1倍短縮した。プロジェクト全体を通じて最大の単発改善効果であり、複合カーネル区間を1つの数値のままにしておくことの危うさを示す実例として記録に残す。

5.5 ビットストリームパッキング — 係数グループ単位のscatter書き込み

長さ計算→スキャン→スキャッターの3段構成

ビット単位の可変長符号化はグローバルには逐次的に見えるが、規格が持つバイトアライメント境界(3章事実(c))を利用し、「長さ計算 (Pass A) → prefix-sum スキャン (Pass B) → スキャッター書き込み (Pass C)」という定型パターンに帰着させた。粒度は当初 precinct/band 単位を検討したが、band幅がDWT分解レベルごとに約60〜1920まで桁違いに分散し、SIMT実行モデルではワープ全体が最も重いスレッドに律速されるため、係数グループ単位まで踏み込む設計に修正している。

significance(1bit/group)
固定長のためPass A不要。各スレッドがビット位置を直接計算し、アライメント済みatomicOrで書き込む
gcli / data(可変長)
128スレッドによるblocked partition局所スキャン + __shfl_up_syncによるワープ単位exclusiveスキャンでオフセットを求め、Pass CでatomicOrスキャッター

当初はband単位で部分並列化したが、1 packetあたりのband数が平均約3にとどまり128スレッド中ごく一部しか稼働しない構造的な非効率が残った。band単位ではなく係数グループ単位のフラットなスキャンに設計を変更したことで、この非効率を解消している。data(可変長ニブル書き込み)は「通常グループ」と「末尾の端数グループ」を有効レーン数1パラメータで統一した単一の計算式に置き換え、逐次的な左シフト状態機械を状態を持たない直接計算式へ再設計した。

5.6 チャンネルデインターリーブ — GPUパイプラインへの統合

CPU側 約1.5ms相当の隠れコストを排除

PPMのRGBRGB…インターリーブ入力は、当初CUDA外のCコードで事前にプレーナ化してから両パスへ渡していた。これをCUDA Graph 1の内部に組み込んだ専用カーネルへ移し、H2D転送1回とデインターリーブを1回のfusedカーネル(3チャンネルを1パスで同時に書き出す)にまとめた。コンポーネントごとに3回へ分けるとpackedバッファを3回冗長に読み直すことになり、fused版はそれよりも約2倍速いことを実測で確認している。

正直な注記: マルチスレッドCPUとの比較

このマシン(Intel Core Ultra 7 265K, 20論理コア)で threads_num を段階的に上げて実測したところ、4スレッド以降は単調にスケールし、20スレッドでは444 RGB系ファイルで単一スレッド比 約12倍(6.3〜6.5ms)に達した。これは pinned memory 化後のGPU warm時間(約7.0ms)とほぼ互角、わずかにCPUが優位という結果であり、「全コアを使い切ったCPU実装がこのGPU実装に競り勝つ場合がある」ことを示している。GPU側にも host RC二分探索の並列化など残された最適化余地はあるが、本レポート時点でCPU/GPUの優劣を最終的に決着させるものではない。

DWTの帯域効率

DWTは演算強度 約0.44 ops/byte のメモリ帯域律速カーネルであり、実機の理論帯域(約896GB/s)に対する理論下限を大きく上回る実測時間がかかっている——現状の帯域利用効率は理論ピークの約29%にとどまる。ブロックサイズ調整(Step B1)は開発機・実機いずれでも有意な改善が確認できず、バンド単位のshift融合(Step B2)は約7〜9%、NLT融合(Step B3)は約3%の改善にとどまった。DWTのメモリトラフィック削減という方向のアプローチ単体では、理論値ほどの改善が実機で得られにくいことが複数回の実験で確認されている。

07 / 08

規格適合性の独立検証

これまでの正しさの検証はCPU参照実装とのbit-exact比較のみであり、実際のJPEG XS規格適合性(他社デコーダでの復号可能性)は検証していなかった。そこでISO/IEC 21122-5公式リファレンスソフトウェア(JPEG XS test model, XSM v3.0.2-ED3、著作権者: intoPIX SA / Fraunhofer IIS / Canon Inc)をISO公式サイトから導入し、評価目的ライセンスに従いこのリポジトリのgit管理下には含めず、スクラッチ領域のみでビルド・検証した。

この検証を通じて、CUDA移植そのものとは無関係な、ベースC実装(CPU/CUDA共通コード)側の規格適合バグを2件発見・修正した。

Bug 1

derive_stream_profile_ppih() が実際の垂直分解レベル数 decom_v を考慮せずプロファイルを宣言していた。デフォルトの ndecomp_v=2 はMainプロファイルの制約(最大垂直分解レベル1)を超えており、生成された全ビットストリームが規格上非適合な宣言のまま出力されていた。420/444/4444では decom_v>1 でHighプロファイルを宣言するよう修正。422/400はISO/IEC 21122-2自体にHigh相当のcodewordが定義されておらず、規格上の既知の制限として文書化した。

Bug 2

名前付きプロファイル(Main/High)を宣言する場合、ISO参照ソフトは slice_height=16 を要求するが、サンプルアプリはPhase 4aのスコープ決定により単一slice(slice_height=画像高さ)を採用していた。既存のホスト側precinctオフセット/バイト長配列を使い、GPUカーネル自体には一切手を入れず、slice境界ごとの範囲memcpy + ヘッダ挿入によるマルチslice組み立てをホスト側に実装して解決した。

検証結果

上記2件の修正後、testdata 3ファイル全てがISO参照デコーダで exit:0 の復号成功に到達した。444 RGB系の実写2ファイルはPSNR 43.87dB / 42.69dB(bpp=4)を記録し目視でも劣化は確認できず、合成テストパターンである1080p YUV422ファイルのみ低PSNR(14.62dB)だったが、これは非圧縮性の乱数パターンを4:1圧縮した結果として正常な挙動であることを切り分け済みである。

08 / 08

結論と今後の課題

4K・10bit静止画1枚のCUDAエンコードは、実機RTX 5070 Tiのwarm状態で約9〜10msを達成し、16ms理想目標・33ms現実目標のいずれも満たした。正しさはCPU参照とのbit-exact一致に加え、ISO/IEC 21122公式リファレンスデコーダによる独立検証でも確認済みである。この過程で、量子化カーネルの2次元grid化という単一の修正が、ビットストリームパッキング段の入念な最適化(係数グループ単位scatter化)を上回る改善効果を持っていたことは、大きな複合カーネル区間を1つの数値として計測し続けることのリスクを示す教訓として残る。

残る最適化候補としては、(1) DWTカーネル自体のより構造的な再設計(水平・垂直リフトの1レベル内融合、大規模変更のため未着手)、(2) host RC二分探索(CPU側、約1.16ms)のGPUオフロード、(3) 他のtestdataファイルでの内訳再現性確認、が挙げられる。

ストレッチゴール: 1フレーム2ms以内は実現可能か

実機での最終内訳(graph1 約7.1〜8.0ms、host RC 約1.16ms、graph2 約1.55ms、合計 約9〜10ms)を起点に、2msというさらに踏み込んだ目標が射程に入るかを検討する。

2msバジェットに対する現状の内訳(概算、budgetは点線ではなく赤線で表示)
2ms 目標

帯: graph1(DWT主体) / host RC / graph2。現状合計 約9.9ms のうち、2ms(赤線)はDWT単体の理論下限にすら届かない位置にある。

結論から言えば、現行のステージ分割・アーキテクチャのままでは2msは非現実的と考えられる。根拠は次の2点である。

  • DWTの理論下限が既に2msの大半を占める。 DWTは演算強度 約0.44 ops/byteのメモリ帯域律速カーネルであり、開発機(224GB/s)での実測から算出した1コンポーネントあたりの理論下限(約3.66ms)を実機の理論帯域(約896GB/s、開発機比 約4倍)へ単純換算すると、3コンポーネント合計でもなお 約2.7〜3ms という下限が残る。これは現状の帯域利用効率(約29%)を仮に100%まで理想的に引き上げられたとしての数字であり、量子化・Pack・host RCを一切含めない時点で既に2msの予算を使い切ってしまう。
  • host RC二分探索はGPU最適化の範囲外にある。 現在CPU側で単一スレッド実行しているprecinct単位の二分探索(約1.16ms)は、2つのCUDA Graphの間に挟まる構造上、GPUカーネルをどれだけ最適化してもこの時間は削れない。単体で2msバジェットの半分以上を占めるため、2ms達成にはこの処理自体をGPUへ移すか、次フレームの処理と重ねて隠蔽するかのいずれかが前提条件になる。

量子化・Packは既に大幅な高速化を終えており(合計 約1.55ms、うちPack単体は約0.25ms)、残された伸びしろは小さい。一方でDWTのメモリトラフィック削減アプローチ(Step B1〜B3)は3回の実装でいずれも数%程度の改善にとどまっており、帯域効率の抜本的な改善には水平・垂直リフトの構造自体を作り直すレベルの再設計が必要になると見込まれる。

結論(未検証の推定であることを明記)

2ms/frameは、DWTの帯域効率を現状から大きく引き上げること(理論上の下限自体がバジェットの過半を占めるため、単なるチューニングでは足りない)と、host RC二分探索をクリティカルパスから外すこと(GPU化またはフレーム間パイプライニングによる隠蔽)の2つの構造的な変更を同時に行って初めて射程に入る、非常に野心的な目標である。現時点でこれらはいずれも未実装・未検証であり、本節はロードマップ上の見立てとして記録するに留める。
